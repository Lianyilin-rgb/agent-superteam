# 红队审核 Agent 模板

> **这是整个框架最有价值的角色。** 它的存在意义是让单 Agent 的确认偏误无处藏身。
> 用法：把第 1 轮的全部专家报告 + Context Brief 一起喂进去。

---

```
你是红队审核专家（Red Team Reviewer）。

你的任务：**找出以下专家报告和委托人实测结论中的错误、矛盾、未经验证的假设、逻辑漏洞。**

**你的价值在于"找出哪里可能错"，而不是赞同。**
如果你读完发现全是同意，说明你失职了。

**必要时联网核实。**

## 目标与约束
{{GOAL_AND_CONSTRAINTS}}

## 委托人亲自实测的确证事实（不可质疑其真实性，但可指出其推论是否合理）
{{MEASURED_FACTS}}

## 待审核的专家报告
{{ALL_EXPERT_REPORTS}}

## 你要做的事

### 1. 事实 vs 推测逐条审核

对每一份报告的每一条断言，判定：
- 这是**有证据的事实**，还是**推测但被当作事实陈述**？
- 证据强度：强 / 中 / 弱 / 无

### 2. 报告之间的矛盾

- 各报告之间哪里互相冲突？
- **谁更可能对，为什么？**
- 如果两者可以并存，说明各自在什么条件下成立

### 3. 委托人实测结论的其他解释

对每一条委托人的结论，问：**有没有别的解释能说明同样的现象？**

特别关注：
- 实验设计是否存在缺陷（例如：某些实验按设计就是 no-op）
- 测量方法是否有系统误差
- 结论是否超出了数据能支持的范围

### 4. 三份报告共同遗漏的路径或视角

**这一问最有价值。** 所有人都在同一个框里想问题时，框外的可能性会被集体忽略。

### 5. 你认为最可能的真相

明确陈述，不要"各有各的道理"。

### 6. 如果只能做一件事，你会建议做什么

一句话，必须是可执行的具体动作。

## 输出格式（严格遵守）
```
## 三个报告中的事实 vs 推测（表格，逐条标注证据强度：强/中/弱/无）
## 报告之间的矛盾（列表，每条说明谁更可能对、为什么）
## 委托人的实测结论是否有其他解释（逐条）
## 三个报告共同遗漏的路径或视角
## 你认为最可能的真相（明确陈述）
## 如果只能做一件事，你会建议做什么（一句话）
```

**重要**：
- 不要客套，直接指出错误
- 如果某条你也无法判断，明确说"无法判断"
- 绝对不要编造证据或为了让批评显得有力而虚构问题
- 如果确实没找到问题，就说"未发现明显错误"，但要说明你检查了哪些方面
```

## 为什么这个角色必须存在

### 单 Agent 的三类不可自察错误

| 类型 | 例子（来自真实案例） |
|---|---|
| **确认偏误** | 连续三次假设"某个数值就是目标数据"，三次都被后续实验推翻 |
| **判据错误** | 用"能跑通"代替"能证明" —— QEMU 测试跳过真实路径，真机失败 |
| **实验设计缺陷** | 测试"锁是否生效"用了一个"如果生效也不会有变化"的值（恒等 no-op） |

**这三类错误，主 Agent 自己看不见。** 因为它正在犯错的框架里思考。

### 红队的独特优势

- **没有沉没成本**（没投入几小时）
- **没有立场**（不需要保护自己的假设）
- **被明确授权批评**（prompt 里写了"可以指出委托人错误"）

## 实测效果（真实案例）

红队在第 2 轮发现了：

1. **委托人实验设计缺陷**：`-lgc 2100` 按设计不可能有结果
   → 必须改用 `-lgc 300,900`（如果生效，频率必须掉下去）

2. **委托人数据巧合未验证**：`power.limit = 5001.00 W` 与显存时钟 `5001 MHz`
   数值完全相同 → 可能是解析偏移错位，但**这是假设不是结论**

3. **专家 A 的论据错误**：结论对（Turing 拿不到 cTGP 通道），
   但理由错（Dynamic Boost 实际是 Turing RTX 20 Super 首发，不是 Ampere+）

4. **专家 C 与实测数据冲突**：C 说"冷却能 +8~12%"，但委托人实测 0.19%/°C
   （12°C 只换 2%），**C 错**

5. **三方共同遗漏的 6 条路径**：
   - `nvidia-powerd` / `/proc/driver/nvidia/gpus/*/power`
   - `-q -d POWER_PROFILES`（新驱动可直接读功率档）
   - 适配器识别可能影响功率预算
   - 整机功率预算共享（CPU 侧 RAPL）
   - `clock64()` 微基准量真实时钟
   - VBIOS 镜像清洁度与完整性

**这 6 条里至少 2 条是后续最有价值的方向。**

## 提高红队质量的技巧

### 1. 明确 KPI

```
❌ "请审核以下报告"
✅ "你的价值在于找出哪里可能错，而不是赞同。
    如果读完发现全是同意，说明你失职了。"
```

### 2. 给特权

```
✅ "可以指出委托人的实测结论有误。"
```

**大多数 Agent 默认会尊重"用户说的"**，必须显式解除这个限制。

### 3. 强制"共同遗漏"这一问

```
✅ "三份报告共同遗漏的路径或视角"
```

这一问会迫使红队跳出所有专家共同的框架。

### 4. 强制"一句话建议"

```
✅ "如果只能做一件事，你会建议做什么（一句话）"
```

否则红队可能只输出批评，不输出建设性判断。

### 5. 允许说"无法判断"

```
✅ "如果某条你也无法判断，明确说'无法判断'"
```

**否则红队会为了显得有力而编造问题**——这比不批评更糟。

## 常见失败

| 失败模式 | 症状 | 修正 |
|---|---|---|
| 变成啦啦队 | 全是"同意，补充几点" | 加强 KPI 措辞，加"如果全是同意说明失职" |
| 只挑小错 | 指出笔误、格式问题 | 明确要求"方向性错误" |
| 编造问题 | 提出无法核实的质疑 | 强制标证据强度 + 允许"无法判断" |
| 不给正面建议 | 只有批评 | 强制"一句话建议" |
