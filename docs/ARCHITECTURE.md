# 架构设计：为什么要这样组织

## 一、单 Agent 决策的三种结构性缺陷

不是模型不够强，而是**信息结构**有问题。

### 缺陷 1：确认偏误不可自察

单 Agent 一旦形成初步假设，后续所有搜索都会不自觉地偏向支持它。

**真实案例**（`examples/mx450-case/`）：
```
假设："10000 mW 这个值就是功率表"
  → 在 VBIOS 里搜到两处 10000 → "找到了！"
  → 反汇编后发现是 x86 的 imul ecx,ecx,0x2710 数学常数 → 推翻
  → 又假设"POW 字符串就是功率表" → 实为错误提示文案 "PLEASE POWER DOWN..."
  → 第三次假设才靠 QEMU + acpi_call 交叉验证收敛
```
三次错误假设，**每次都自我感觉"找到了"**。

### 缺陷 2：验证判据的自我欺骗

最危险的错误不是"没验证"，而是**验证了一个错误的命题**。

**真实案例**：
```
验证目标：initrd 拼接是否有效
使用判据：QEMU -append 'rdinit=/bin/sh' 能进 shell
问题：rdinit=/bin/sh 强制跳过 initramfs 的 /init 脚本
结论：判据通过 ≠ 真实启动路径可用
后果：真机启动失败，退到 (initramfs) shell
```

**红队的价值就在于此**：它会问"你这个验证，究竟验证了什么？"

### 缺陷 3：非技术约束缺席

纯技术 Agent 只回答"能不能做到"，不回答"值不值得"。

**真实案例**：
```
技术上：改 ACPI 表可以让 GPU 功率上限 +50%
代价上：需要重启生产 NAS，该机 ZFS 池已 SUSPENDED 过、有 5 个永久错误
        且 systemctl reboot 会卡在卸载该池（实测卡 15 分钟）
红队算账：停机 1 次期望损失 ¥425（最坏 ¥7,600）
          性能收益 ¥0–1,000/年
          → 风险收益比 1:7.6 到 1:∞
```

**这个账，技术专家不会算。必须有一个专职算账的角色。**

## 二、为什么是这四个角色

### 专家（Expert）—— 提供领域纵深

- **职责**：在自己领域内给出有证据的判断
- **禁止**：跨领域下结论
- **输出要求**：每条结论必须标注证据强度

### 红队（Red Team）—— 专门否证

- **职责**：找出所有人（包括用户）的错误
- **KPI**：找到的错误数量，**不是**"表示同意"
- **特权**：可以指出委托人的实测结论有误
- **必须回答**："如果只能做一件事，你建议做什么"

**为什么必须有它**：主 Agent 有沉没成本（已经投入几小时），红队没有。

### 激进派（Aggressive）—— 找上限

- **职责**：在约束内追求最大收益
- **禁止**：用"风险大"作为不做的理由
- **输出要求**：命令级的可执行步骤 + 预期收益 + 成功概率

### 稳健派（Conservative）—— 算代价

- **职责**：优先保证系统可用性与数据安全
- **KPI**：不把生产环境搞挂
- **输出要求**：红线清单 + 停机成本定量 + 明确"继续/收手"

### 综合者（Synthesizer）—— 你（主 Agent）

- **职责**：裁决，**必须指出各方的事实错误**
- **禁止**：简单平均（"各方都有道理"是最差的裁决）
- **必须产出**：分档执行计划 + 明确停止线

## 三、为什么第 1 轮必须并行且互不可见

如果专家 A 看到专家 B 的报告，会发生两件事：

1. **锚定**：A 会不自觉地接受 B 的框架，减少独立发现
2. **礼貌性同意**：A 会弱化与 B 冲突的结论

**并行独立**是保证"交叉"有意义的前提。三份报告**互不引用**，冲突才会暴露。

**真实案例中的收获**：

| 冲突 | 价值 |
|---|---|
| A 说"TGP 在 VBIOS 里" vs B 说"移动版 VBIOS 可能无功率墙" | 红队裁决：两者可并存 —— VBIOS 可以把策略编码在 **PMU 消费的内部段**里，同时**不提供宿主可读的功率表**（这正好解释 `5001 W` 回读） |
| C 说"1575 是上限" vs 实测 `SUPPORTED_CLOCKS` 有 2100 | 红队裁决：`SUPPORTED_CLOCKS` 是全 SKU 覆盖的档位表，"表里有" ≠ "本机可达" |
| C 说"冷却能 +8~12%" vs 用户实测 0.19%/°C | 红队裁决：**C 错**，用户数据更可信（受控、可重复） |

**如果没有并行独立，这三处冲突都会被"礼貌"掉。**

## 四、为什么必须"证据分级"

不分级时，"我搜到一个帖子说……"和"官方文档明确写……"会被同等对待。

**四级标准**：

| 级别 | 判据 | 可作决策依据？ |
|---|---|---|
| **强** | 官方文档 / 源码 / 可复现实测 | ✅ 可以 |
| **中** | 第三方报告，未独立复现 | ⚠️ 只能作假设 |
| **弱** | 单一轶事、社区传闻 | ❌ 不能 |
| **无** | 推测，无任何证据 | ❌ 必须标注"不确定" |

**真实案例中的应用**：
```
专家 C 称"ThinkBook 15 在 15W/69°C 稳 1575 MHz"
红队判定：证据强度【弱】
理由：未能核实原始来源；且若为游戏实测则不可比
      —— 游戏常吃不装满功耗墙，会自己摸到 boost 上限；
         拿轻负载对照 GEMM 满载是方法论错误
```

**这一条阻止了一个可能误导整个决策方向的结论。**

## 五、为什么方案必须带"停止线"

没有停止线的方案会无限延伸：

```
试 A → 无效 → "那试试 B" → 无效 → "那试试 C" → ...
```

每一轮都消耗时间、增加风险，但**没有退出条件**。

**停止线的语法**：
```
"如果 <实验 X> 证明 <命题 Y> 不成立，则接受 <Z> 为最终值，不再投入。"
```

**真实案例中的停止线**：
```
第 0 档做完若 `-lgc 300,900` 完全无效
  AND `Target Temp` 开 GSP 后仍是 N/A
  → 接受 2.09 TFLOPS 为天花板，收手
```

**这条线把一个开放式探索变成了有限次实验。**

## 六、成本模型

以 5 个 Agent、每个约 3000 token 输出计算：

| 项 | 量 |
|---|---|
| 上下文总量 | ~20k token |
| 人工阅读时间 | 15–25 分钟 |
| 产出 | 3 份专家报告 + 1 份红队审核 + 2 份决策 + 1 份裁决 |

**收益不是"更快的答案"，而是"更少的方向性错误"。**

真实案例中，红队发现的两个事实错误（`-lgc` 实验设计缺陷、`5001` 数值巧合）如果没被发现，会导致后续投入全部白费。
