# 常见失败模式（必读）

> 全部来自真实踩坑记录。每条都注明**症状 → 根因 → 正确做法**。

---

## A 类：验证判据错误

### A1. 用"能跑通"代替"能证明"

**症状**：QEMU 测试通过 → 以为真机能启动 → 实际启动失败

**根因**：用了 `-append 'rdinit=/bin/sh'`，强制跳过 initramfs 的 `/init` 脚本。
只验证了"内核能解包归档"，**完全没验证"完整启动流程"。**

**正确做法**：
```
判据必须覆盖真实路径。
如果要验证 A → B → C 三步，不能只验证 A。
"能进 shell" ≠ "能挂载 root" ≠ "能进 systemd"
```

### A2. `cmd > file 2>&1` 污染归档文件

**症状**：cpio 归档 9226 字节，`mod 512 = 10`、`mod 4 = 2`（完全不对齐）

**根因**：`cpio -H newc --create > out 2>&1` 把 cpio 输出到 **stderr 的统计信息**
（`18 blocks\n`，10 字节）一起灌进了归档尾部。

**正确做法**：
```bash
# ❌ 错
find dir | cpio -H newc --create > out 2>&1

# ✅ 对（stderr 必须丢弃）
find dir | cpio -H newc --create > out 2>/dev/null

# 验证（三项全过才算过）
stat -c %s out                        # 大小
echo $(( $(stat -c %s out) % 512 ))   # 必须为 0
tail -c 64 out | od -A d -t x1z       # 尾部必须干净
grep -c 'blocks' out                  # 必须为 0
```

### A3. `file` 和 `cpio -itv` 都是假验证

**症状**：`file` 报 "ASCII cpio archive"、`cpio -itv` 能列出内容 → 以为归档没问题

**根因**：
- `file` 只检查**头部 magic**
- `cpio -itv` 遇到 `TRAILER!!!` 就**停止解析**

**两者都看不见尾部的垃圾数据。**

**正确做法**：必须同时检查 头部 / 总大小 / 对齐 / 尾部 hexdump。

### A4. 实验设计本身是恒等 no-op

**症状**：`nvidia-smi -lgc 2100` 返回 "All done"，时钟不动 → 判定"驱动不支持"

**根因**：如果 `-lgc` 单值语义是"只设 max"，而实际运行频率本来（1320）就低于 2100，
那这个设置**按设计就不可能有任何可观测效果**。

**正确做法**：
```
测试"锁是否生效"，要用一个"如果生效必然产生变化"的值。
❌ -lgc 2100（当前跑 1320，设 2100 是 no-op）
✅ -lgc 300,900（如果真的锁住，频率必须掉到 ≤900）
```

## B 类：假设当事实

### B1. 数值巧合当证据

**症状**：在 VBIOS 里搜到 `10000`（mW）两处 → 判定"找到功率表"

**根因**：反汇编显示是 `imul ecx,ecx,0x2710` / `div ecx` —— **x86 数学常数**。

**正确做法**：
```
任何"在二进制里搜到目标值"的发现，必须做上下文验证：
- 反汇编该区域
- 检查是否落在代码段而非数据段
- 检查是否有结构化的表头
```

**同类案例**：`power.limit = 5001.00 W` 与显存时钟 `5001 MHz` 数值**完全相同**
→ 高度疑似 VBIOS 解析偏移错位读到了显存字段。**但这是假设，不是结论**，
必须用"修正偏移后重解析"来验证。

### B2. 打包工具的行为未验证

**症状**：cpio 归档缺少 `kernel/`、`kernel/firmware/`、`kernel/firmware/acpi/` 三个目录条目

**根因**：用了 `find kernel -type f`（`-type f` 只匹配文件，丢掉了目录）。

**后果**：内核解包时 `sys_open("/kernel/firmware/acpi/X.aml")` 因父目录不存在而失败
（`init/initramfs.c` 的 `do_name()` 不会自动创建父目录）→ 扰乱 initramfs 状态
→ 后续 `/init` 挂载 root 失败 → 退到救援 shell。

**正确做法**：
```bash
# ❌ 错（丢目录）
find kernel -type f | cpio -H newc --create > out
# ✅ 对
find kernel | cpio -H newc --create > out 2>/dev/null

# 验证目录层级
cpio -itv < out | head -4
# 应看到 drwxr-xr-x 的三行目录
```

### B3. 假设某个机制可用

**症状**：用 `GRUB_EARLY_INITRD_LINUX_CUSTOM` 让 GRUB 加载两个 initrd 文件 → 启动 panic

**根因**：`initrd /boot/a.cpio /boot/b.img` 这种**多文件拼接**在目标机器上不可靠。

**正确做法**：
```
需要多个归档时，在文件层面预先拼接成单文件：
  cat a.cpio b.img > combined.img
再用单文件加载。这样不依赖引导器的多文件实现。
```

## C 类：非技术约束缺席

### C1. 没算停机成本

**症状**：为了 +8% 性能，让生产 NAS 重启 3 次，其中 2 次启动失败

**根因**：只算"技术收益"，没算"可用性损失"。

**正确做法**：每个需要重启/高风险的动作，必须明确：
```
停机时长 × 小时成本 + P(失败) × 恢复成本
vs
预期性能收益（年化）
```

### C2. 忽略"目标用途"决定收益是否成立

**症状**：花两小时优化 GPU SM 时钟

**根因**：如果该 GPU 的主要用途是**视频转码**，而 `NVENC/NVDEC` 是**独立硬件块、
有自己的时钟域**，那么 SM 超频对转码收益 **= 0**。

**正确做法**：先确认"瓶颈是否在被优化的维度上"。跑一次负载画像（7 天利用率）。

### C3. 在脆弱底座上做实验

**症状**：ZFS 池已有 5 个永久元数据错误、`systemctl reboot` 会卡住 15 分钟，
仍然在上面反复重启做实验

**正确做法**：
```
先修底座，再做上层实验。
或者：建立"安全断电检查点"（如 zpool export 后再重启），
      把不可控的尾部风险清零。
```

## D 类：团队协作失败

### D1. 礼貌性同意

**症状**：三份专家报告结论高度一致，没有冲突

**诊断**：这通常意味着**它们看到了彼此的输出**，或者任务描述里已经有倾向性。

**正确做法**：
- 第 1 轮必须**并行**、**互不可见**
- 任务描述里不能出现"我认为应该 X，请验证"

### D2. 红队变成啦啦队

**症状**：红队报告全是"同意以上观点，补充几点……"

**诊断**：红队的 prompt 没有明确规定 KPI。

**正确做法**：红队 prompt 必须包含：
```
"你的价值在于找出哪里可能错，而不是赞同。"
"可以指出委托人的实测结论有误。"
"如果某条你也无法判断，明确说'无法判断'。"
```

### D3. 综合裁决变成平均

**症状**："激进派说得有道理，稳健派也有道理，建议综合考虑"

**诊断**：这是**最差的裁决**，因为它没有做决策。

**正确做法**：必须：
```
1. 指出各方的事实错误（每方至少一条）
2. 给出明确的分档执行计划
3. 给出明确的停止线
```

## E 类：破坏性操作

### E1. 把"记录"当作"修复"

**症状**：`zpool clear` 之后池显示 HEALTHY → 以为修好了

**根因**：`clear` 只清零错误计数器，**不修复永久错误**，且会**抹掉"哪些文件已损坏"的清单**。

**正确做法**：`zpool status -v` 先记录受害者清单，再谈 clear。

### E2. 强制断电

**症状**：`systemctl reboot` 卡住 15 分钟 → 长按电源键

**根因**：`systemctl reboot` 会尝试正常卸载所有文件系统；ZFS 池有 IO 错误时会卡死。

**正确做法**：
```bash
# 正确姿势
zpool export <pool>          # 先导出（写入最终 uberblock，干净关闭）
sync; sync
systemctl reboot             # 此时不会卡

# 导出后再断电是安全的（这是唯一例外窗口）
```

### E3. 在没验证恢复路径的情况下改启动链

**正确做法**：
```
1. 改之前备份所有相关文件
2. 用"独立菜单项"而不是"改默认项"（失败只需重启）
3. 明确写出"失败后按哪几个键恢复"
4. 首次测试时人必须在机器前
```

## 快速自检清单

动手前问自己：

- [ ] 我要验证的命题，**准确表述**是什么？
- [ ] 我的判据，**只**能证明这个命题吗？会不会证明了别的？
- [ ] 如果实验成功/失败，**分别意味着什么**？
- [ ] 这个实验**可能完全无效**（no-op）吗？
- [ ] 我用的是"事实"还是"推论"？
- [ ] 有没有**其他解释**能说明同样的现象？
- [ ] 失败后怎么回滚？**具体到按键**？
- [ ] 有没有更便宜的方式获得同样的信息？
- [ ] 我的**停止线**在哪里？
