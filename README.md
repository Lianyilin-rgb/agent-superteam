# Agent Superteam — 多角色交叉审核决策框架

> 让 AI Agent 团队**互相否证**，而不是互相附和。
> 一个可复用的、面向硬技术决策的开源工作流。

---

## 它解决什么问题

单个 AI Agent 做技术决策时，有三种系统性盲区，且**它自己看不见**：

| 盲区 | 表现 | 真实案例（本仓库 `examples/mx450-case/`） |
|---|---|---|
| **确认偏误** | 只找支持自己结论的证据 | 我连续三次假设"10000 mW 就是功率表"，三次都被自己的后续实验推翻 |
| **验证判据错误** | 用"能跑通"代替"能证明" | QEMU 测试用了 `rdinit=/bin/sh`，跳过了真正的 `/init` 流程 → 真机启动失败 |
| **忽略非技术约束** | 只看"技术上能不能" | 没算过：为了 +8% 性能，让生产 NAS 停机 3 次、损失 5 个 ZFS 元数据块 |

**单 Agent 无法自我否证**。它需要一个专门找错的角色，和一个专门算代价的角色。

## 核心思路：四角色 + 一轮交叉

```
                    ┌─────────────────┐
                    │  Context Brief  │  ← 已确证事实（不含推论）
                    └────────┬────────┘
                             │
        ┌────────────────────┼────────────────────┐
        │                    │                    │
   ┌────▼────┐         ┌─────▼─────┐        ┌─────▼─────┐
   │ 专家 A  │         │  专家 B   │        │  专家 C   │   第 1 轮：并行调研
   │ 领域 1  │         │  领域 2   │        │  领域 3   │   （互相不可见）
   └────┬────┘         └─────┬─────┘        └─────┬─────┘
        └────────────────────┼────────────────────┘
                             │
              ┌──────────────┼──────────────┐
              │              │              │
        ┌─────▼─────┐  ┌─────▼─────┐  ┌─────▼──────┐
        │  红队     │  │ 激进派     │  │  稳健派     │          第 2 轮：交叉审核
        │ 只找错    │  │ 最大化收益 │  │ 最小化风险  │          （独立判断）
        └─────┬─────┘  └─────┬─────┘  └─────┬──────┘
              └──────────────┼──────────────┘
                             │
                    ┌────────▼────────┐
                    │   综合裁决      │  ← 必须指出各方的事实错误
                    │  + 停止线       │  ← 必须写明"什么时候放弃"
                    └─────────────────┘
```

**关键设计**：
- **并行独立**：第 1 轮三个专家互相看不见，避免锚定
- **强制否证**：红队的 KPI 是"找出错误"，不是"表示同意"
- **证据分级**：每条结论必须标注 强 / 中 / 弱 / 无
- **强制列出不确定**：每个角色必须写"我不确定的地方"
- **停止线**：方案必须包含"做到什么程度就放弃"

## 快速开始

### 1. 写一份 Context Brief

用 `templates/context-brief.md`。**只写已确证的事实，不写推论。**

```markdown
## 目标
## 硬约束
## 已确证事实（附测量方法与数值）
## 已排除路径（附否证方法）
## 待决策问题
```

### 2. 启动第 1 轮（三专家并行）

从 `agents/` 选三个视角，把 `agents/expert.md` 的模板填上 Context Brief。

### 3. 启动第 2 轮（红队 + 双决策）

把第 1 轮的全部输出喂给 `agents/red-team.md`、`agents/aggressive.md`、`agents/conservative.md`。

### 4. 综合裁决

用 `templates/decision-record.md` 产出 ADR 风格的决策记录。

## 真实案例：MX450 算力提升（`examples/mx450-case/`）

一个完整的、未删改的实战记录，包含：

- **3 份专家报告**（EC/PMU、VBIOS、性能调优）
- **红队审核报告**（指出了两处我方事实错误 + 五处专家错误）
- **激进派决策**（预测 +6~25%）
- **稳健派决策**（建议收手，含定量风险收益模型）
- **最终裁决与停止线**

**这个案例的价值在于它展示了"团队真的吵架"**：

| 冲突点 | 激进派 | 稳健派 | 红队裁决 |
|---|---|---|---|
| 该不该继续 | 继续，能拿 25% | 收手，风险收益比 1:∞ | 两者都有事实错误 |
| `Target Temp = N/A` | 是病灶，开 GSP 能修 | 说明固件不支持，没救 | 双方都没验证"谁消费这个值" |
| `-lgc 2100` 无效 | 驱动不支持 | 同左 | **这个实验按设计就不可能有结果** |
| 5001 W 哨兵 | VBIOS 解析错位读到显存时钟 | "无意义字段" | 数值巧合需验证，不能当证据 |

## 五条核心原则

### 1. 事实与推论必须分离

```
❌ "功率表在 VBIOS 里"                    ← 推论当事实
✅ "VBIOS 已提取，但六种编码均未找到功率表"  ← 事实
```

### 2. 每一个"验证通过"必须说明验证的是什么

```
❌ "QEMU 测试通过"                        ← 通过了什么？
✅ "QEMU 能解包 initramfs 并进入 shell，但未验证完整 /init 流程"  ← 边界清晰
```

### 3. 强制写"我不确定的地方"

每个角色的输出模板都有这一节，**留空视为不合格**。

### 4. 证据分级不可省略

| 级别 | 含义 |
|---|---|
| **强** | 有官方文档 / 源码 / 可复现实测 |
| **中** | 有第三方报告，但未独立复现 |
| **弱** | 单一轶事、社区传闻 |
| **无** | 我的推测，未找到任何证据 |

### 5. 方案必须带停止线

```
"如果 X 实验证明 Y 不成立，则接受 Z 为最终值，不再投入。"
```

**没有停止线的方案不是方案，是许愿。**

## 适用 / 不适用

**适用**：
- 硬件逆向、固件修改、系统调优等**高风险技术决策**
- 有多条互斥路径需要排序
- 决策成本高、失败代价大（生产环境、不可逆操作）

**不适用**：
- 事实查询（直接搜索更快）
- 有唯一正确答案的技术问题
- 时间压力极大、必须立刻动手的场景
